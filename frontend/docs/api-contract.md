# Контракт фронтенда RepairCalc

Контракт интерфейса RepairCalc; HTTP-сервер находится в `backend/backend_java`. Это не описание готового API «Максидома» / Bagisto: при интеграции понадобится адаптер данных каталога.

## Подключение и режимы

Плавающая кнопка **«Тестовый режим»** открывает настройки. Переключатель `MOCK — использовать заглушки`:

- включён: все запросы обслуживает `src/services/mock.ts`; HTTP к API не выполняется;
- выключен (`NOT MOCK`): каждый запрос выполняется через `fetch` к настроенному API. Ошибки не включают моки обратно.

Адрес по умолчанию: `http://127.0.0.1:8000/api/v1`. Его можно изменить в панели или задать через `VITE_API_URL` в `.env`. Сохранённый в панели адрес имеет приоритет над `.env`. Адрес включает префикс API и не содержит query/hash. Настройки режима сохраняются в `localStorage`.

При переключении режима / адреса старое рабочее пространство размонтируется. Новый каталог и проекты загружаются с выбранного источника. Данные и подтверждения MOCK не отправляются в HTTP-режим. При возврате в MOCK восстанавливаются локальные данные.

Задержка 0 / 350 / 1200 мс и сценарии `Обычный ответ`, `Ошибка ML-сервиса`, `Пустой результат` действуют только на заглушки. Пустой сценарий возвращает пустой подбор, отсутствие разобранной комнаты или отсутствие новых классификаций. Он не удаляет сохранённые привязки. Журнал показывает источник, метод, путь, результат и длительность последних запросов.

## Транспорт

- Запросы и ответы: JSON, UTF-8. Без дополнительной обёртки `{ data: ... }`.
- Заголовок `Accept: application/json`; у запросов с телом также `Content-Type: application/json`.
- `credentials: omit`: авторизация и cookie-сессии в этой версии не реализованы.
- Таймаут: 8 секунд. Устаревшие запросы чтения отменяются через `AbortController`.
- Сервер должен разрешать CORS для origin фронтенда, включая `OPTIONS`, `GET`, `POST`, `PUT`, `Content-Type`, `Accept`.
- Ошибочные HTTP-статусы, не-JSON и несовместимые структуры отображаются как ошибка с повтором запроса. Цена и количество не заменяются вычислением на моковых данных.
- Типы DTO: `src/services/contracts.ts` и `src/data.ts`. Проверка входящих ответов: `src/services/client.ts`.

## Каталог и рабочее пространство

`Bootstrap`:

```ts
{
  products: Product[];
  projects: Project[];
  favorites: string[];  // product IDs
  regions: string[];
  guides: { title: string; tag: string; time: string; text: string }[];
}
```

`products` должен содержать все товары, на которые ссылаются загруженные проекты. `id` — строковый уникальный ключ. Если `projects` пуст, фронтенд предлагает создать первый проект на материалах полученного каталога. В нём должны быть доступные покрытия для пола и стен.

`Product`:

```ts
{
  id: string;
  name: string;
  brand: string;
  category: 'floor' | 'walls' | 'prep' | 'electric';
  price: number;       // целые рубли за единицу продажи
  unit: string;       // «упак.», «ведро», «рулон», «шт.» и т.д.
  coverage: number;   // положительная полезная площадь единицы продажи
  wet: boolean;
  heavy: boolean;
  rating: string;
  description: string;
  color: string;      // цвет визуального образца
  texture: string;    // wood / stone / tile / paint / linen / can / bag / socket
}
```

Для преобразования Bagisto: `id` сохраняйте отдельно от SKU и исходного `cod_good`; `price` DTO формируется из возвращённой магазином итоговой цены `result_price` за соответствующую единицу продажи. Цена упаковки и цена м² не взаимозаменяемы. Полные характеристики необходимо получать из полной карточки, а не присваивать товару фильтры категории. Этот адаптер в текущем проекте не реализован.

`Workspace` — `{ projects: Project[], favorites: string[] }`. `PUT /workspace` заменяет рабочее пространство целиком и возвращает принятый снимок. Создание, переименование, дублирование и удаление проектов, добавление и изменение комнат, избранное используют этот метод. Записи последовательно отправляются фронтендом, чтобы старый ответ не перезаписал новую правку. При ошибке изменения остаются на экране, отмечаются несохранёнными и могут быть отправлены повторно.

`Project`:

```ts
{
  id: string; name: string; updatedAt: string;
  object: 'Квартира' | 'Дом' | 'Студия';
  repair: 'Косметический' | 'Капитальный' | 'Дизайнерский';
  reserve: 5 | 10 | 15;
  labor: boolean;
  rooms: Room[]; // минимум одна комната
}
```

`Room`:

```ts
{
  id: string; name: string;
  type: 'living' | 'kitchen' | 'bathroom' | 'bedroom' | 'kids' | 'balcony';
  length: number; width: number;  // 0,5–30 м
  height: number;                // 2–6 м
  windows: number; doors: number; // целые 0–10
  wet: boolean; heavy: boolean;
  floor: string; wall: string;   // product IDs соответствующих категорий
}
```

UUID новых проектов и помещений генерируется фронтендом; сервер принимает эти идентификаторы. Валидация допустимости материалов выполняется и во фронтенде, и должна повторяться сервером.

## Расчёты

`Estimate`:

```ts
{
  items: {
    product: Product;
    quantity: number;  // целое число единиц продажи
    cost: number;
    rooms: string[];  // названия помещений
    surface: number;
  }[];
  materials: number;
  labor: number;
  total: number;
  totalArea: number;
  categories: {
    id: 'floor' | 'walls' | 'prep' | 'electric';
    name: string; color: string; total: number;
  }[];
}
```

Все суммы — неотрицательные рубли. Сервер отвечает за согласованность итогов, строк и категорий. CSV и печать используют полученную смету. Во время пересчёта экспорт недоступен, предыдущие цифры скрываются.

`ProductCalculation` — `{ quantity: number, unit: string, total: number }`. Вход `surface` — площадь в м²; для электротоваров — количество точек. `reserve` — процент запаса, включая `0`, если выключен переключатель запаса. Возвращаемое количество целое. Карточки товаров и цены выбранных покрытий обращаются к этому эндпоинту.

Геометрия плана, арифметика площади для визуализации и проверка полей остаются задачей клиента; цены, сметы и ML-ответы в NOT MOCK не вычисляются заглушкой.

## Описание комнаты

```ts
type ParsedRoom = {
  draft: Omit<Room, 'id' | 'floor' | 'wall'> | null;
  extracted: string[];     // что извлечено явно
  assumptions: string[];  // что предположено и требует проверки
  clarification: string | null;
};
```

Фронтенд показывает редактируемое подтверждение. Только действие «Добавить в проект» создаёт комнату, присваивает UUID и выбирает совместимые покрытия из текущего каталога. При `draft: null` показывается уточнение. После изменения текста старый результат сбрасывается, незавершённый запрос отменяется.

## Рекомендации и объяснения

Приоритет `priority`: `balanced` / `budget` / `durability`.

```ts
type RecommendationResult = {
  summary: string;
  groups: {
    category: 'floor' | 'walls';
    candidates: {
      productId: string;
      score: number;       // 0..1, оценка соответствия, не метрика точности модели
      reasons: string[];
      tradeoff: string;
      quantity: number;
      total: number;
      evidence: { title: string; excerpt: string; source: string }[];
    }[];                  // порядок ранжирования задаёт сервер
  }[];
  excluded: { productId: string; reason: string }[];
};
```

`groups: []` — корректный пустой ответ. Только товары текущего каталога с совместимыми условиями доступны для применения. В интерфейсе есть альтернативы, объяснения, справочные выдержки и ограничения. В MOCK все оценки и источники явно отмечены как примеры; они не выдаются за результат запущенной модели или проверенную нормативную документацию.

## ML-привязки

```ts
type Assignment = {
  productId: string;
  works: ('flooring' | 'painting' | 'wallpaper' | 'tiling' | 'preparation' | 'electrical')[];
  rooms: Room['type'][];
  score: number; // 0..1
  explanation: string;
  status: 'pending' | 'approved' | 'rejected';
};
```

`POST /ml/classify` возвращает предложения для выбранных товаров. Фронтенд не подтверждает их автоматически. Можно выбрать несколько работ и помещений. Для подтверждения нужны непустые `works` и `rooms`; результат сохраняется через `PUT /ml/assignments/{productId}`. Повторное открытие показывает сохранённые привязки.

## Админка и метрики успеха

Ресурсы персонала находятся по адресам `#admin/matching` и `#admin/metrics`. `#admin` и старый `#matching` открывают мастерскую. Это организация интерфейса; авторизация и роли пока не реализованы. Для эксплуатации необходимо добавить проверку доступа персонала к административным и ML-методам на сервере и согласовать авторизацию клиента.

`GET /admin/metrics` возвращает единый отчёт за указанный сервером период. Запрос выполняется только при открытии вкладки метрик и по кнопке обновления. Ошибки не заменяются моками или нулевыми значениями. В MOCK возвращается фиксированный иллюстративный отчёт; задержка тестового режима действует, сценарии ошибки / пустого ответа ML относятся только к `/ml/*`.

```ts
type MetricsReport = {
  generatedAt: string; // ISO 8601 с часовым поясом
  period: { from: string; to: string }; // ISO 8601, [from, to), отображение в UTC
  modelVersion: string;
  dataset: string; // имя и версия размеченного сабсета
  labeledProducts: number;
  matching: { id: string; name: string; tp: number; fp: number; fn: number }[];
  consumption: {
    id: string; name: string; unit: string;
    samples: number; // число сопоставленных строк эталонных смет
    absoluteError: number; // сумма |расчётное количество − эталонное количество|
  }[];
  automation: { automatic: number; eligible: number };
  estimates: { completed: number; totalSeconds: number; p95Seconds: number | null };
  journey: { started: number; completed: number; totalClicks: number };
  requests: { total: number; failed: number };
};
```

- `matching` содержит **все согласованные топ-категории MVP**, включая строки с нулевыми счётчиками, если по категории нет наблюдений. Для каждой оцениваются связи «товар → вид работ» на размеченном сабсете. Precision = TP / (TP + FP), recall = TP / (TP + FN), F1 = 2TP / (2TP + FP + FN). Цель — F1 ≥ 0,8 в каждой категории; карточка показывает минимальный F1. При отсутствующей оценке хотя бы одной категории общий результат — «Нет данных». Порог сравнивается до округления.
- `consumption`: одинаковые исходные параметры, запас и единица продажи. MAE = `absoluteError / samples`, отдельно для каждой группы / единицы. Упаковки и рулоны не усредняются вместе. Для нескольких единиц одной категории нужны разные `id`.
- `automation`: уникальные товары, автоматически принятые без ручной разметки, / все уникальные товары, участвовавшие в автоматическом сопоставлении за период. Ручные подтверждения из мастерской не увеличивают `automatic`.
- `estimates`: успешные расчёты за период; время от запроса до готового ответа в секундах. Среднее = `totalSeconds / completed`. P95 вычисляет сервер по исходным длительностям, фронтенд не усредняет перцентили. `null` означает отсутствие P95.
- `journey`: когорта сценариев, начатых за период. Начало — событие «выбрал комнату», завершение — «готовая корзина» до конца периода. `totalClicks` суммирует клики только завершённых сценариев, включая стартовое и завершающее действия. Среднее = `totalClicks / completed`; доля завершения = `completed / started`. Серверу нужно согласовать дедупликацию и идентификатор сценария с аналитикой клиента.
- Готовая корзина — отдельное событие интеграции с магазином; просмотр сметы и экспорт CSV им не являются. В текущем прототипе нет сбора этих событий: MOCK показывает пример отчёта, HTTP ожидает настоящую агрегацию.
- `requests`: завершившиеся запросы расчёта и ML за период; `failed` — ошибки сервиса, таймауты и сетевые ошибки, без пользовательских отмен. Доля ошибок = `failed / total`.
- Все счётчики — неотрицательные безопасные целые. Время и сумма абсолютных ошибок — конечные неотрицательные числа. Числители долей не превышают знаменатель. При отсутствии наблюдений суммы равны нулю, `p95Seconds: null`; деление на ноль отображается прочерком. `matching: []` и `consumption: []` — допустимое отсутствие оценок. `generatedAt ≥ period.to ≥ period.from`, `id` уникальны внутри массивов.
- Числовой порог задан только для F1. Цели по MAE, времени, кликам, автоматизации, завершению и ошибкам необходимо согласовать после базового замера; интерфейс не выдаёт их за утверждённые KPI.

## Проверка без реализации сервера

`tests/ml-runtime.spec.ts` проверяет MOCK-сценарии и HTTP-транспорт через перехват сетевых запросов Playwright: методы, пути и тела, серверные данные, ошибки соединения, некорректный JSON-контракт и изоляцию режимов. Это тестовый стенд фронтенда, а не поставляемый бэкенд.

`tests/admin.spec.ts` проверяет навигацию и сохранение разметки после смены вкладки, точный порог F1, расчёт долей и MAE по серверным данным, ошибки и повтор запросов, отсутствие наблюдений, изоляцию MOCK / HTTP, мобильные размеры и доступность через axe-core.
## Отправки смет и обратная связь по подбору

`POST /engagement/events` сохраняет подтверждённое действие. Примеры JSON:

```json
{"id":"54b9e99e-21a4-41b6-8428-a51c9bcf0ef1","visitorId":"96b74932-38ad-4b56-98af-08fd2815c6c3","kind":"share","projectId":"project-default-1","method":"clipboard"}
```

```json
{"id":"f7569599-0b1a-46b2-b5f9-94b7c8c28f31","visitorId":"96b74932-38ad-4b56-98af-08fd2815c6c3","kind":"rating","rating":5}
```

Ответ: `200 {"id":"<UUID события>"}`. `id` и `visitorId` — UUID. Для `share`
обязательны непустой `projectId` до 200 символов и `method` (`native` или `clipboard`),
`rating` отсутствует. Для `rating` обязательна целая оценка 1–5, `projectId` и `method`
отсутствуют. Неверные данные возвращают 400. Идентичный повтор возвращает 200 без
новой строки; изменение содержимого существующего события возвращает 409.
Время события задаёт сервер. Смета и её текст в статистике не сохраняются.

Клиент создаёт UUID для сеанса второго этапа калькулятора и использует его как
идентификатор оценки. Изменения материалов не открывают закрытое окно повторно.
При повторе после ошибки сохраняются UUID и оценка.
Кнопка «Поделиться» сама по себе не создаёт события: оно отправляется после
успешного `navigator.share()` или `navigator.clipboard.writeText()`.
Это подтверждение передачи браузером, а не доставки сообщения адресату.

`GET /admin/metrics` дополнен полем `engagement`:

```json
{
  "since": "2026-10-29T12:00:00Z",
  "shares": {"total": 3, "visitors": 2},
  "ratings": {"total": 2, "distribution": [0, 0, 0, 1, 1]}
}
```

Здесь `since` — дата первого события (null при отсутствии событий), все счётчики
накоплены за всё время независимо от периода демонстрационных ML-метрик.
`distribution` содержит ровно пять неотрицательных целых чисел для оценок 1–5;
их сумма равна `ratings.total`. Среднее вычисляется по этому распределению,
при отсутствии оценок показывается прочерк. `shares.visitors` считает различные
`visitorId` только среди отправок. Идентификатор живёт в хранилище браузера;
очистка данных или другое устройство создаёт нового посетителя.

Поле `engagement` необязательно для совместимости с прежними API: его отсутствие
показывается как недоступная статистика, а не нулевые значения. MOCK использует
отдельное хранилище `repaircalc.mock.engagement.v1` с реальными действиями текущего
браузера. NOT MOCK читает и записывает `repaircalc.engagement_events`; таблицу
создаёт миграция `server/migrations/005_engagement.sql`.
