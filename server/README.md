# RepairCalc — PostgreSQL, Redis и pgAdmin

Рабочее хранилище для MVP RepairCalc по двум предоставленным документам. Реализованы 30 таблиц, три последовательные SQL-миграции, проверки целостности, роли и Docker Compose. Это слой данных; HTTP API, импорт реального каталога, ML inference и вычислитель формул ещё не реализованы.

## Подключение на этом ПК

| Сервис | Адрес | Учётная запись |
|---|---|---|
| PostgreSQL 17.11 | `127.0.0.1:5433`, БД `repaircalc` | `repaircalc_app` или `repaircalc_reader` |
| Redis 7.4.11 | `127.0.0.1:6380` | `app` |
| pgAdmin 9.18 | <http://127.0.0.1:5443> | `admin@repaircalc.dev` |

Пароли находятся в **CONNECTIONS.private.md** и `.secrets/credentials.json`. Эти файлы исключены из Git; права доступа к локальным секретам ограничены владельцем, SYSTEM и администраторами. Для коллег передавайте только нужную учётную запись. Общую административную карточку целиком передавать не требуется.

В pgAdmin уже зарегистрированы два подключения: приложение и чтение. При открытии подключения введите соответствующий пароль PostgreSQL. Это отдельный пароль от входа в pgAdmin. В обоих подключениях установлен `sslmode=disable`, параметры сертификатов удалены.

По запросу владельца TLS отключён у всех трёх сервисов. Сертификаты не требуются. Соединения идут без шифрования: HTTP и Redis передают пароли открытым текстом, PostgreSQL использует SCRAM для проверки пароля, но запросы и данные остаются незашифрованными. Адрес панели начинается с `http://`, даже при порте 5443.

## Интернет

На момент проверки WAN-адрес роутера — `94.19.3.127`, адрес этого ПК — `192.168.3.100`. Настройка роутера остаётся за владельцем, как согласовано в чате:

| Протокол | Внешний порт | Внутренний адрес | Внутренний порт |
|---|---:|---|---:|
| TCP | 5433 | 192.168.3.100 | 5433 |
| TCP | 6380 | 192.168.3.100 | 6380 |
| TCP | 5443 | 192.168.3.100 | 5443 |

После проброса адрес pgAdmin: <http://94.19.3.127:5443>. PostgreSQL: `94.19.3.127:5433`; Redis: `94.19.3.127:6380`.

Внешняя доступность ещё **не подтверждена**. Запросы независимого проверочного сервиса вернули HTTP 403 и не дали результата проверки портов. Проверку надо выполнить с другого интернет-подключения после проброса. Проверка с этого ПК по собственному WAN IP не заменяет её.

На активном интерфейсе Ethernet профиль Windows — Public; firewall для Public и Private при проверке был выключен. Эти настройки не менялись. Добавить отдельные разрешающие правила текущий процесс не смог из-за отсутствия прав администратора. При включённом firewall выполните в **PowerShell от администратора**:

```powershell
.\scripts\Enable-Firewall.ps1
# Если известны адреса коллег, можно ограничить источники:
# .\scripts\Enable-Firewall.ps1 -RemoteAddress @('IP_КОЛЛЕГИ')
```

На роутере желательно закрепить DHCP-адрес `192.168.3.100`. При изменении публичного IP достаточно обновить адрес у клиентов.

## Команды для коллег

Пароль вводится по запросу:

```text
psql "host=94.19.3.127 port=5433 dbname=repaircalc user=repaircalc_reader sslmode=disable" -W
redis-cli -h 94.19.3.127 -p 6380 --user app --askpass PING
```

`repaircalc_app` имеет права работы с данными, `repaircalc_reader` — только чтение. `repaircalc_migrator` может выполнять DDL через роль `repaircalc_owner`; его пароль предназначен сопровождающему схемы. Superuser `repaircalc_admin` по сети запрещён, доступен через локальный сокет внутри контейнера. Для персональных доступов нужны отдельные роли; текущие учётные записи общие для соответствующих задач.

Redis отключает пользователя default, разрешает приложению ключи только `repaircalc:*` и запрещает административные команды. Пароль администратора Redis нужен только сопровождающему.

## Запуск и сопровождение

На этом ПК секреты и образы уже подготовлены:

```powershell
.\scripts\Start.ps1
docker compose ps
.\.venv\Scripts\python.exe tests/test_storage.py
.\.venv\Scripts\python.exe tests/test_pgadmin_connections.py
.\.venv\Scripts\python.exe scripts/manage.py backup
.\.venv\Scripts\python.exe scripts/manage.py restore-test --file backups/ИМЯ_КОПИИ.dump
```

`restore-test` создаёт отдельную БД со случайным именем; рабочую `repaircalc` не перезаписывает. Проверочные БД и volumes оставлены для осмотра. Для восстановления на другом сервере сначала создайте роли из локального bootstrap либо перенесите их отдельно: `pg_dump` не включает глобальные роли и пароли. Локальную папку `.secrets` и Docker volumes также следует резервировать отдельно. Redis содержит только восстанавливаемый кеш.

Остановка с сохранением данных: `docker compose stop`. Миграции применяются под advisory lock, в одной транзакции, с проверкой SHA-256 уже применённых файлов. Изменения схемы добавляйте новым файлом в `migrations/`.

На другом ПК первоначальная подготовка:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-tools.lock.txt
docker pull postgres:17.11-alpine
docker pull redis:7.4.11-alpine
docker pull dpage/pgadmin4:9.18
.\.venv\Scripts\python.exe scripts/setup.py
.\scripts\Start.ps1
```

Создание секретов повторно поверх существующих запрещено скриптом. Карточка `CONNECTIONS.private.md` содержит текущие адреса этого развёртывания; при переносе замените их. Compose использует `pull_policy: never`: обновление образов выполняется явно. Использованные идентификаторы образов записаны в `docs/images.lock.json`.

Windows bind mounts здесь недоступны: Docker сообщил `user declined directory sharing`. Скрипт `sync-config.py` копирует конфигурацию через `docker cp` в три отдельных named volumes. Изменение файлов `config/` требует `sync-config.py` и перезапуска сервисов. Volumes конфигурации объявлены external, чтобы случайный `compose down -v` не удалил их; volumes данных при такой команде всё равно будут удалены.

## Модель и ограничения

Подробности — `docs/SCHEMA.md`, результаты — `docs/VALIDATION.md`.

Реальные товары, ставки и формулы не выдуманы и не загружены. Начальные данные: семь единиц измерения и внутренний город `ru-spb`; это не ID региона каталога. Испытательные записи создавались в транзакциях с rollback. Значения последовательностей после проверок могут иметь пропуски.

Перед интеграцией нужны отсутствующий документ «03_Общий_контракт», URL и авторизация каталога, подтверждение семантики региона и `result_price`, согласование единиц и версий контрактов с backend/ML. Текущая схема — реализованное предложение v0.1 по доступным требованиям, а не утверждённый межкомандный контракт.
