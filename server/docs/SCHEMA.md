# Модель хранения v0.1

| Область | Таблицы | Правила |
|---|---|---|
| Справочники | `unit`, `city`, `catalog_source`, `catalog_region` | Исходные ID строковые; внутренний город отделён от региона API |
| Версии каталога | `catalog_snapshot`, `catalog_head`, `import_issue` | Сначала loading; публикация только целой версии с проверенной региональной семантикой |
| Карточки | `product`, `product_card`, `catalog_category`, `product_category`, `product_stock` | Стабильная идентичность товара, карточки по версиям, отдельные категории и складские строки |
| Таксономия и ML | `taxonomy_version`, `work_type`, `model_version`, `mapping_proposal`, `manual_mapping_decision` | ML-предложения отделены от неизменяемой истории ручных решений |
| Формулы | `formula_version`, `consumption_parameter` | Версия реализации, входы, округление, параметры карточки и доказательство утверждения |
| Стоимость работ | `labor_contractor`, `labor_source`, `labor_observation`, `labor_rate_version`, `labor_rate_member` | Независимый подрядчик, URL, хеш свидетельства, город, состав, условия, единица, вид цены, проверка |
| Смета | `estimate`, `estimate_room`, `estimate_material_line`, `estimate_material_allocation`, `estimate_labor_line`, `estimate_labor_evidence` | Версии, входы, значения цен, параметры, трасса расчёта, распределение по комнатам и исходные наблюдения |

## Каталог

Уникальность карточки: `UNIQUE(snapshot_id, product_key)`. У снимка уникальна пара `(source_id,version)`, у товара — `(source_id,product_id)`. Составные внешние ключи запрещают смешивать источник и версию. `id`, `sku`, `cod_good` различаются; внешние коды — `text`, ведущие нули сохраняются.

Сырые ответы хранятся в JSONB, нормализованные ключи, цены, единицы и отношения — в отдельных колонках. Атрибуты могут расширяться; фильтры списка не считаются характеристиками SKU. Остатки хранятся по исходным складам без придуманного суммирования.

Импорт выполняется в loading-снимок. Повторные записи обрабатываются импортёром через `ON CONFLICT`; ограничение уникальности защищает БД. `expected_cards` должен соответствовать проверенному объёму импорта. Вызов `SELECT repaircalc.publish_catalog(snapshot_id)` проверяет полные карточки, количество, ошибки страниц, критические import_issue, семантику региона и циклы категорий. Только затем атомарно переключает `catalog_head`. Старые опубликованные снимки остаются неизменяемыми. Прямое изменение head приложению запрещено.

Триггеры изменений дочерних строк берут блокировку снимка, чтобы не допустить вставку в момент публикации. Конкурирующие публикации сериализованы advisory lock. Массовый импорт в один снимок из множества независимых транзакций следует измерить перед масштабированием; это MVP с упором на целостность.

## Ручные решения и версии

`effective_manual_mapping` возвращает последнее ручное решение по товару, версии таксономии и типу работы. Новая модель добавляет предложения, не переписывая ручное решение. Смена версии таксономии требует явного переноса решений; автоматического переноса между несовместимыми таксономиями нет.

Таксономия, модели, формулы, утверждённые параметры и решения дополняются новыми версиями. Семантическое объединение ML-предложений с ручными решениями должно реализоваться API: само наличие предложения ещё не утверждает привязку.

## Ставки и сметы

Наблюдение хранит фиксированную цену или цену «от», состав работы, условия и включение материалов. Утверждение требует известного исключения материалов и автора проверки. Опубликованная версия ставок включает утверждённые наблюдения одного города; наблюдения для одной строки сметы должны совпадать по типу работ, единице, виду цены, составу и условиям.

Для денег используется `NUMERIC(18,2)`, для количества — `NUMERIC(20,6)`. Проверки отвергают отрицательные значения, NaN и переполнение. `null` обозначает неизвестное значение и сохраняется в подытогах. Цена «от» имеет нижнюю границу и неизвестную верхнюю. `line_total`, `total_lower`, `total_upper` — вычисляемые колонки с округлением до двух знаков.

Смета собирается в `draft`. После заполнения строк её финализируют обновлением `state='final'`, `finalized_at`, подытогов и `calculation_status`. Триггеры проверяют источники, соответствие версий, цен, валюты, единиц, параметров и итогов. Полный результат требует известных количеств и сумм; цена «от» остаётся partial из-за неизвестной верхней границы. Распределение общей потребности по комнатам, если задано, должно сходиться с потребностью строки. После final запрещены изменения сметы, комнат, строк и доказательств.

Строка покупки может агрегировать один SKU между комнатами до округления; дробная потребность и целое число покупаемых упаковок хранятся раздельно. Геометрическая проверка площади, совместимость партий, значение расхода, доказательная проверка свидетельства и реализация формулы относятся к backend. JSON-контракты, их размеры и пределы входов необходимо закрепить с ним; БД не исполняет формулы и не проверяет реальность URL/документа.

## Индексы и эксплуатация

Индексы обслуживают чтение карточки по версии и товару, поиск последних ручных решений, фильтры наблюдений по городу/работе/единице, историю смет и связи внешних ключей. GIN для всех сырых JSONB не создавался: подтверждённого запроса по их содержимому нет. Партиционирование и реплики для текущего неопределённого объёма не добавлялись. Проверки на больших промышленных данных и нагрузочные p95 не выполнялись.

Redis: ключи `repaircalc:catalog:{version}:product:{id}`, `repaircalc:estimate:{contract}:{request_hash}`; рекомендованный TTL назначает backend. Включены AOF everysec, volume данных, лимит 256 MiB и allkeys-lru. Поэтому Redis предназначен для восстановимого кеша; состояние очередей, гарантированная идемпотентность и единственная копия сметы должны храниться в PostgreSQL либо в отдельно согласованном хранилище.
